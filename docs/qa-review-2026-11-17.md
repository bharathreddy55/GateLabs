## Fix first — P1

### QA-01: Untrusted text becomes executable HTML

**Confirmed:** a saved Community entry containing a harmless local HTML event handler executed a JavaScript marker. No external request, token reading or exfiltration was used. Community is currently device-local, so this is not evidence of a remotely published cross-user attack. It proves the unsafe rendering boundary. Imported formula fields, practice content and assistant messages also interpolate unescaped values into HTML by source inspection.

**Locations:** `src/pages/Community.js:86`, `src/pages/Community.js:89`, `src/pages/Assistant.js:76`, `src/pages/Formulas.js:427`, `src/pages/Practice.js:199`.

**Impact:** imported, restored or externally produced content can run as page code instead of being displayed as text. This is especially concerning because AI keys are stored in JavaScript-readable localStorage.

**Improve:** use text nodes or context-appropriate escaping for plain text; use a well-defined sanitizer for allowed rich text/Markdown; validate URL schemes and attribute values. Add tests for posts, replies, formulas, AI responses and imported question fields. OWASP recommends safe text sinks and sanitization for intended HTML: [XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

### QA-02: Save failures are swallowed and can produce a false success

**Confirmed:** the actual Firebase adapter resolved successfully when the cloud write failed. It also resolved when both its localStorage write and cloud write failed. The runner treats a resolved call as a recorded attempt.

**Locations:** `src/config/firebase.js:1118`, `src/pages/ExamRunner.js:79`.

**Improve:** return an explicit result such as `{localSaved, cloudSaved, pendingSync}`. Show “saved on this device” separately from “synced.” If neither succeeds, retain/export the result and show a blocking error. Queue retries and only confirm deletion after the requested persistence operations succeed.

### QA-03: Legacy study data carries between accounts

**Confirmed:** after Alice saved a bookmark and syllabus progress, switching the actual adapter's current user to Bob still returned Alice's data. Attempt isolation tests pass because attempts were updated to use account-specific keys; legacy tools were not.

**Locations:** `src/config/firebase.js:1302`, `src/config/firebase.js:1331`, `src/pages/Formulas.js:262`, `src/utils/aiService.js:32`.

**Improve:** scope all personal storage by user ID, including bookmarks, checklist progress, custom formulas and AI configuration; define explicit migration/ownership rules for old keys. Test sign-out and account switching for every feature, not only attempts. Never silently assign old shared device data to a new account.

### QA-04: The AI server handler accepts anonymous requests using its configured key

**Confirmed locally:** a POST with no authentication reached a stubbed provider and returned 200 when a dummy server API key was configured. The handler has no authentication, authorization, rate limiting or payload-size checks and returns `Access-Control-Allow-Origin: *`.

**Location:** `api/gemini.js:20`.

**Impact is conditional:** if deployed with a working server key, this route could allow unauthorized usage and spend. No production endpoint or real key was exercised.

**Improve:** verify Firebase ID tokens, enforce user quotas/rate limits and request-size/model allowlists, set bounded upstream timeouts, and return controlled errors. Restrict CORS where appropriate; CORS alone is not authorization. Review the actual deployed rules separately: [Firebase rules conditions](https://firebase.google.com/docs/firestore/security/rules-conditions).

### QA-05: The legacy ingestion parser corrupts five-option answer keys

**Confirmed:** a five-option question whose correct answer was E became four options with `correctAnswer: 0` in `parseTextQuestions`. The newer exam parser handles this correctly; the old global question ingestion path still uses the other parser. AI-assisted import instructions also explicitly allow missing keys to become option A.

**Locations:** `src/config/firebase.js:550`, `src/config/firebase.js:642`, `src/pages/Practice.js:843`.

**Improve:** consolidate on one typed question schema and validated parser. Reject or quarantine missing/unrecognized keys. Preserve MCQ/MSQ/NAT types, fifth options where applicable, numeric ranges, passages and diagrams. Never publish a guessed placeholder as a correct answer.

### QA-06: Practice cannot render a valid NAT question

**Confirmed:** a legitimate numeric-answer question with `type: NAT` and no options throws `Cannot read properties of undefined (reading 'map')`. Existing practice controls also use radio inputs and single-option answer checking for all questions, so MSQ handling is incomplete by inspection.

**Location:** `src/pages/Practice.js:203`.

**Improve:** share the question renderer and answer evaluation logic with the exam engine: MCQ radio selection, MSQ checkboxes, NAT numeric input and range checking. Cover each type in both practice and timed modes.

### QA-07: The assistant invents a generic explanation when no AI service is connected

**Confirmed:** asking “What is 2 + 2?” without a key produced a canned discussion of GATE runtime complexity and the Master Theorem. A provider failure also substitutes generic text while describing it as a conceptual explanation.

**Location:** `src/pages/Assistant.js:136`.

**Improve:** show a clear disconnected/error state with a settings action and retry. Use an explicitly labelled sample/demo only if needed. Preserve the question so it can be retried. Render Markdown/math safely rather than showing raw `**` and LaTeX commands.

## Make the app look and feel better

1. **Finish applying one design system.** New exam screens use the blue workspace style; Formulas/Assistant retain purple gradients and About retains the older marketing layout. Use shared header, card, button, typography and spacing components. Keep About within the signed-in shell when opened from the workspace. Update About, README and metadata to describe all supported exams and current capabilities.
2. **Fix the formula grid before adding decoration.** In the desktop check, a card's outer box was about **515 px** high while its visible front face was about **264 px**. This produces a large empty strip before the next row. Size the card and both faces from one defined height, or replace the 3D flip with an accessible “Show explanation” disclosure.
3. **Make primary reading text 14–16 px.** Keep helper text around 12–13 px. Some visible captions remain below 12 px. Put exam identity, next action and real progress ahead of badges and explanatory boilerplate. Validate actual contrast in both themes rather than relying on colour names.
4. **Give mobile tabs a visible continuation cue.** At 320 and 390 px the tab strip intentionally scrolls, but Progress is off-screen. Add a trailing fade/arrow, auto-scroll the selected tab into view and preserve a visible selected state. Keep the page itself free of horizontal scrolling.
5. **Make exam results easier to act on.** Lead with score, accuracy, time and save status. Add “Wrong only,” “Unanswered” and “Bookmarked” filters to the compact runner review, and make “Practise weak topics” the next action. Keep full-paper and section-practice results visibly distinguished.
6. **Simplify the paper library at scale.** SBI has 18 cards. Add paper-type filtering and status, sort ready papers before invalid ones, and show question count, duration and difficulty/coverage consistently. Keep long provenance/technical import notes behind a disclosure.
7. **Make Progress the single source of truth.** Show per-section syllabus completion and last practice date alongside scores. Avoid displaying “0” when remote history is simply loading or unavailable; use a loading/offline state.
8. **Keep controls useful without external icons.** The shared sidebar has inline SVGs, while older pages show empty icon blocks when the icon CDN fails. Bundle critical icons or use the same inline icon set throughout.

### Keyboard and accessibility findings

- All **16 formula cards** were non-focusable divs without button semantics; card flipping cannot be operated as a normal keyboard button.
- The mobile drawer opens and Escape closes it, but Tab can move into obscured background controls while the drawer stays open. Use proper dialog/drawer focus management and make the background inert while open.
- Formula search, assistant input and forum search lack a programmatic label in the inspected default states. Placeholder text should not be the only label.
- Add full keyboard tests for modals, tab navigation, question navigation, answer clearing, review marking and result filters. Test with at least one actual screen reader. This review is not a formal WCAG conformance result.

## Architecture and test improvements

- Extract a shared typed question renderer and consolidate the two parser paths.
- Centralize versioned, validated user storage. Use IndexedDB for larger banks and answer snapshots; keep a bounded local cache and explicit cloud sync queue.
- Move content ingestion out of every student's browsing flow. Separate public question reads from authenticated publisher writes.
- Load routes and heavy features on demand. The build currently loads all pages through eager imports; Chart.js, Firebase and PDF tooling should be evaluated independently for lazy loading.
- Introduce route cleanup for charts, timers and listeners, and replace full innerHTML refreshes where a small state update is sufficient.
- Bring Firestore rules and emulator tests into the repository. No deployed-rules permission claim is made from client code alone. Firebase config values in a web app are not, by themselves, proof of a leaked secret.
- Move browser-test dependencies into the project's declared dev dependencies/lockfile. Current tests rely on a Codex runtime installation and a Windows Chrome path; clean CI machines cannot run them as-is.
- Add CI that runs unit tests, browser tests and build, with fixtures plus a Firebase-emulator job. Cover the failure cases found here, not only successful examples.
- Independently review educational answer keys and syllabus coverage. Exact counts and valid options do not establish difficulty calibration, correctness or completeness.

## Suggested implementation order

1. **Data and trust:** QA-01 through QA-07; deploy/test appropriate rules and API protections.
2. **Persistence:** one attempt repository, complete backup/restore, migration, auth restoration and typed storage recovery.
3. **Core learning workflow:** repair four SBI sources, finish typed practice, live palette status, durable result links and honest offline states.
4. **Visual consistency:** formula layout, About shell, typography, mobile tab cues, uniform tokens and icons.
5. **Release verification:** real auth and cloud checks in a test project, cross-browser/screen-reader testing, dependency advisory scan and measured performance under a realistic network.
